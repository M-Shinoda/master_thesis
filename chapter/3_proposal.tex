\chapter{提案手法}
  
本章では，YouTubeライブ配信コメントを継続的に収集・分析するための基盤設計と，その設計方針について述べる．
本研究では，以下の3点を提案する．

\begin{enumerate}
    \item \textbf{データ収集ソースの拡張}: 従来のX（旧Twitter）に依存せず，YouTubeライブ配信コメントを新たなSNSデータソースとして活用する．両プラットフォームの仕様を比較し，収集可能性と特性の違いを明確にする．
    
    \item \textbf{持続的な収集・蓄積・分析基盤の設計}: 平常時から災害時まで一貫してデータを収集し，構造化された形で蓄積・分析できる基盤を提案する．サーバレス環境とIaCを活用し，低コストかつスケーラブルな構成とする．
    
    \item \textbf{多角的分析手法の統合}: 感情分析（BERT, LUKE-WRIME）と可視化（LookerStudio, Webダッシュボード）を組み合わせ，市民の情動変化を即時的に把握可能とする．
\end{enumerate}

以下，各提案内容の設計方針について述べる．

  \section{全体アーキテクチャ}

  提案する基盤の全体構成を\figref{fig:system_overview}に示す．本基盤は，データ収集層，蓄積層，分析層，可視化層の4層から構成され，各層が疎結合に設計されているため，個別の拡張や変更が容易である．

  \input{figure/system_overview}

  \begin{itemize}
      \item \textbf{データ収集層}: YouTube Data API v3を用いたポーリング方式によるコメント取得．サーバレス環境（AWS Lambda）で定期実行し，低コストで持続的な収集を実現．
      \item \textbf{蓄積層}: Google Cloud BigQueryを採用し，時間パーティショニングによる効率的なクエリ処理とストレージ最適化を実現．Infrastructure as Code（Terraform）による環境管理で再現性を確保．
      \item \textbf{分析層}: 感情分析モデル（BERT, LUKE-WRIME）を独立したシステムとして実装．分析結果は蓄積層に再格納され，時系列分析や感情推移の把握に利用可能．
      \item \textbf{可視化層}: LookerStudioによる探索的データ分析（EDA）と，Next.js製Webダッシュボードによる即時的な状況把握の両立．
  \end{itemize}

  以下，各層の設計方針を詳述する．


  \section{データ収集ソースの比較と選定}

  \subsection{XとYouTubeライブ配信コメントの仕様比較}
  
  \input{table/yt_x_comp}
  
  \tabref{tab:yt_x_comp}に両プラットフォームの主要な仕様差を示す．以下，本研究におけるYouTube採用の設計判断根拠を述べる．
  
  \subsubsection{データ取得制約の違い}
  Xでは月100ポスト以上の取得が有償化されており，継続的な大規模収集には経済的障壁が存在する．一方，YouTubeは1日10,000 Quota（約2,000リクエスト相当）まで無償であり，本研究の要求仕様（2分間隔収集）に対して十分な余裕を持つ．
  
  \subsubsection{投稿構造と拡散性の違い}
  Xは単発ポストにリツイート・リプライといった拡散指標を持ち，情報伝播の分析に適する．YouTubeライブコメントは特定配信のチャットストリームであり，視聴者という限定集団内での同期的反応の観測に特化している．本研究では災害時の瞬間的な市民反応の把握を重視するため，後者の特性が適合する．
  
  \subsubsection{コンテンツ形式と保存期間}
  Xは画像・動画を含むマルチモーダルデータだが，YouTubeコメントはテキストのみ（エモート含む）である．また，Xの投稿は永続的にアーカイブされるが，YouTubeライブコメントは配信設定に依存し，本研究対象の配信では数時間程度で遡及不可となる．このため，\textbf{順次的なデータ蓄積が必須}となり，これが本基盤の設計要件となる．
  
  \subsection{YouTubeライブ配信の対象選定}
  
  本研究では，24時間365日リアルタイムで日本全国の地震情報を配信するYouTubeライブチャンネル\cite{youtube}を対象とする．地震発生時に視聴者のコメントが集中し，災害時の市民反応を観測可能な環境が整っている点を評価した．



  \section{データ収集層の設計}

  \subsection{API方式の選定}

  YouTube Data API v3では，ライブチャットコメント取得に2種類のAPIが提供されている（詳細は評価章で述べる）．本研究では\textbf{ポーリング方式（liveChatMessages.list）}を採用する．

  \subsubsection{選定理由：コスト効率とスケーラビリティ}
  
  \begin{itemize}
      \item \textbf{サーバレス環境での実装可能性}: AWS Lambdaのような関数実行環境で定期実行できるため，常時稼働サーバ（EC2等）が不要で運用コストを抑制できる．
      \item \textbf{ストリーミング方式との差異}: リアルタイム性ではストリーミング方式（liveChatMessages.realtime）が優位だが，接続維持コストが高く，本研究の目的（災害時反応の把握）には2分間隔のポーリングで十分な時間解像度が得られる．
      \item \textbf{Quota管理の容易性}: ポーリング頻度を調整することで，1日あたりのQuota消費量を制御でき，無償枠内での持続的運用が可能．
  \end{itemize}

  \subsection{収集頻度の設計}

  YouTube Data API v3の無償Quota（10,000/日）と1リクエストあたりの消費Quota（5）を考慮し，以下の設計とする．

  \begin{itemize}
      \item \textbf{理論上の最短間隔}: 式~\eqref{eq:eq1}より約43秒ごとに取得可能．
      \begin{equation}
          \frac{60\,(\mathrm{sec}) \times 60\,(\mathrm{min}) \times 24\,(\mathrm{hour})}{{10000\,(\mathrm{Quota})}/{5\,(\mathrm{Quota})}}
          = 43.2\,(\mathrm{sec}) \label{eq:eq1}
      \end{equation}
      \item \textbf{実装上の設定}: 余裕を持たせて\textbf{2分間隔}とする．これにより，Quota上限の約3倍の余裕を確保し，API制限やエラーリトライにも対応可能．
  \end{itemize}



  \section{データ蓄積層の設計}

  \subsection{BigQueryの選定理由}

  本基盤では，Google Cloud BigQueryをデータウェアハウスとして採用する．選定理由は以下の通りである．

  \begin{itemize}
      \item \textbf{ペタバイト級のスケーラビリティ}: 時系列で増大し続けるSNSデータの長期蓄積に対応．
      \item \textbf{高速なSQLクエリ処理}: 時間パーティショニングと組み合わせることで，特定期間のデータ抽出を高速化．
      \item \textbf{LookerStudioとのネイティブ連携}: ダッシュボード構築時のデータソース接続が容易．
      \item \textbf{サーバレスアーキテクチャ}: インフラ管理不要で，データ量に応じた従量課金により初期コストを抑制．
  \end{itemize}

  \subsection{Infrastructure as Code（IaC）による環境管理}

  データベーススキーマとインフラ構成をTerraformで定義し，以下の設計原則を満たす．

  \begin{itemize}
      \item \textbf{再現性}: コードベースで環境を再構築可能とし，複数の配信チャンネルへの横展開を容易にする．
      \item \textbf{保守性}: スキーマ変更履歴をバージョン管理し，API仕様変更への追従を迅速化．
      \item \textbf{スケーラビリティ}: 新規配信ソースの追加時，パラメータ変更のみで環境を複製可能．
  \end{itemize}

  \subsection{データスキーマの設計方針}

  YouTube Data API v3のJSONレスポンス構造に対応したスキーマを設計する．主要フィールドの設計方針を以下に示す．

  \begin{itemize}
      \item \textbf{ネスト構造の平坦化}: JSON階層を「親キー\_子キー」形式で展開し，BigQueryのカラム型ストレージに最適化．
      \item \textbf{時間パーティショニング}: コメント投稿時刻（snippet\_publishedAt）をキーとした日次パーティショニングにより，クエリ性能とコスト効率を向上．
      \item \textbf{コメント種別の明示化}: snippet\_typeフィールドにより，通常コメント・スーパーチャット・運営削除通知等を識別可能とする．
  \end{itemize}

  具体的なフィールド構成と実装例は，評価章で述べる．



  \section{感情分析層の設計}

  \subsection{感情分析モデルの選定}

  本基盤では，事前学習済みの日本語感情分析モデルとして以下の2種類を採用する．

  \begin{itemize}
      \item \textbf{BERTbaseJapanese}\cite{bert}: コメントをネガティブ・ポジティブ・ニュートラルの3極性に分類．感情の大まかな傾向把握に適する．
      \item \textbf{LUKE-WRIME}\cite{luke}: 喜び・悲しみ・期待・驚き・怒り・恐れ・嫌悪・信頼の8感情に分類．細粒度な情動変化の分析に適する．
  \end{itemize}

  両モデルともHugging Faceで公開されている事前学習済みモデルを利用し，追加学習なしで適用可能である．

  \subsection{独立システムとしての設計}

  感情分析機能を独立したシステムとして実装することで，以下の設計目標を達成する．

  \begin{itemize}
      \item \textbf{モジュール性}: 収集・蓄積層とは疎結合とし，新たな分析モデルの追加や既存モデルの差し替えが容易．
      \item \textbf{拡張性}: LLM（大規模言語モデル）を用いた災害関連コメントのフィルタリング等，将来的な分析手法の追加に対応．
      \item \textbf{再利用性}: Terraformによるスキーマ定義を流用し，新規分析タスクごとにテーブルを追加可能．
  \end{itemize}

  分析結果は蓄積層（BigQuery）に再格納され，時系列グラフ生成や感情推移分析に利用される．



  \section{可視化層の設計}

  \subsection{二層構造による可視化戦略}

  本基盤では，用途に応じて2種類の可視化手段を提供する設計とする．

  \subsubsection{LookerStudio：探索的データ分析（EDA）}

  BigQueryとのネイティブ連携により，プログラミング不要で以下の分析が可能．

  \begin{itemize}
      \item \textbf{全体傾向の把握}: コメント数の時系列推移，感情分析結果の割合，頻出単語のワードクラウド等を迅速に作成．
      \item \textbf{外部データとの統合}: LookerStudioのコネクタ機能を活用し，P2P地震情報\cite{p2p_earthquake_api}等の外部APIと連携した複合分析が可能．
      \item \textbf{低い学習コスト}: データアナリストが直感的に操作でき，仮説検証サイクルを高速化．
  \end{itemize}

  \subsubsection{Webダッシュボード：即時的な状況把握}

  Next.js + React + BigQuery SDKによるカスタムダッシュボードを構築する．

  \begin{itemize}
      \item \textbf{設定可能なパラメータ}: 時間間隔（5分〜1日），日付範囲（今日/1日指定/期間指定），自動更新間隔（秒単位）を柔軟に設定可能．
      \item \textbf{感情の視覚的表現}: LUKE-WRIMEの8感情分類にプルチックモデル\cite{plutchik1980_psychoevolutionary}を参考にした配色を適用し，直感的な理解を支援．
      \item \textbf{レスポンシブUI}: Tailwind CSSによるモバイル対応で，災害対応現場での利用にも配慮．
  \end{itemize}

  \subsection{可視化における設計判断}

  LookerStudioは柔軟性が高い反面，操作には一定の学習コストを要する．一方，Webダッシュボードは定義済みインターフェースによる即時性を重視する．両者を併用することで，\textbf{探索的分析と定型監視}の双方に対応可能な基盤とする．

  具体的な実装環境，UI設計，運用結果については評価章で述べる．

  \section{まとめ}

  本章では，YouTubeライブ配信コメントを活用した持続的な災害分析基盤の設計方針と具体的な実装を述べた．提案・実装した基盤は以下の特徴を持つ．

  \begin{itemize}
      \item \textbf{データソースの拡張}: Xの制約を補完するYouTubeライブコメントの活用．
      \item \textbf{低コストな持続性}: サーバレス環境とIaCによるスケーラブルな構成．
      \item \textbf{多角的分析と即時可視化}: 感情分析と二層構造の可視化による柔軟な状況把握．
  \end{itemize}

  次章では，約9ヶ月間の運用を通じた有効性検証の結果を述べる．
